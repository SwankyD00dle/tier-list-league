# @tier-list-league/backend

Node HTTP API backed by PostgreSQL, with schema and migrations managed by Drizzle. Runs in Docker.

## Local development

Run the full app from the repository root:

```bash
nvm use
npm install
npm run db:migrate --workspace @tier-list-league/backend
npm run dev
```

The frontend and API share http://localhost:3000. Next.js proxies `/api/*` to the backend's internal listener on port 3001.

To run only the backend:

```bash
cp packages/backend/.env.example packages/backend/.env
npm run dev --workspace @tier-list-league/backend
```

## Run the full app with Docker Compose

From `packages/backend`:

```bash
cp .env.compose.example .env.compose
# Fill in Discord credentials and a random JWT_SECRET.
docker compose --env-file .env.compose up --build -d
```

Open http://localhost:3000. Compose starts PostgreSQL, runs migrations once,
waits for the backend's database health check, then starts the production frontend.
Only port 3000 is published; the frontend proxies `/api/*` to `backend:3001`.
The backend image includes the shared API-schema workspace. Migration tooling lives
in a separate Docker build target so the backend runtime omits development dependencies.

For a platform sandbox, install/start Docker first and bind the platform endpoint
to sandbox port 3000. Set `APP_PUBLIC_URL` to its full HTTPS URL **without a trailing
slash**, set `COOKIE_SECURE=true`, and register
`<APP_PUBLIC_URL>/api/auth/discord/callback` with Discord before starting. Compose
uses the same public URL for the frontend build/start and backend OAuth configuration.
Rebuild when the public URL changes. Keep `.env.compose` out of version control;
Docker builds exclude environment files. The frontend image retains build dependencies
because Next loads its TypeScript configuration at startup.

```bash
docker compose --env-file .env.compose ps -a
docker compose --env-file .env.compose logs migrate backend frontend
curl http://localhost:3000/api/health
```

For a prefixed endpoint, include its prefix in the health-check URL. Database data
lives in a Docker volume on the sandbox disk; it is disposable when the sandbox is
deleted. `docker compose --env-file .env.compose down` retains the volume; adding
`--volumes` deletes it. Configure the sandbox lifetime explicitly for ongoing hosting.

For host-based `npm run dev`, start a separate local PostgreSQL instance exposing
localhost:5432; this deployment Compose intentionally keeps database ports internal.

## Scripts

- `dev` / `start` — run the standalone backend on `PORT` (default 3001).
- `typecheck` — type-check with TypeScript 7 (`tsc-native`).
- `test` / `test:watch` — run route tests with Vitest.
- `db:generate` / `db:migrate` / `db:push` / `db:studio` — Drizzle Kit.
- `seed:default-avatars` — upload the default profile pictures to Vercel Blob and seed their `profile_picture` rows (needs `BLOB_READ_WRITE_TOKEN`).

## Default profile pictures

New users are shown one of 16 built-in avatars until they set their own picture. The avatars are flat, skribbl.io-style SVG faces generated by `scripts/generate-default-avatars.mjs` (repo root) and committed under `assets/default-avatars/`. Regenerate them with `npm run generate:avatars` from the repo root.

The images are hosted on Vercel Blob and recorded as `profile_picture` rows (a default is a row with no `user`, `game`, or `created_by`). To (re)seed them:

1. Create a Blob store in the Vercel dashboard and set `BLOB_READ_WRITE_TOKEN` in `packages/backend/.env`.
2. Run `npm run seed:default-avatars --workspace @tier-list-league/backend`.

The seed is idempotent — it uploads to fixed pathnames (`default-avatars/00.svg` …) and replaces the default rows on each run.

A user's default is chosen deterministically from their id — `defaultAvatarIndex` in `src/profile-pictures/default-avatars.ts` runs a modulo over the seeded defaults, so the same user always gets the same avatar. Wiring this into a `GET /profile-picture` endpoint and the game/user responses is the next step (out of scope here).

## HTTP API

Routes are defined under `src/api/routes/` and registered in `src/api/routes/index.ts`.

| Method | Public path                | Description           |
| ------ | -------------------------- | --------------------- |
| GET    | `/api/health`              | Liveness + DB probe   |
| GET    | `/api/users`               | List users            |
| GET    | `/api/users/:id`           | Get a user by id      |
| GET    | `/api/games`               | List games            |
| POST   | `/api/games`               | Create a game         |
| GET    | `/api/games/:id`           | Get a game by id      |
| PATCH  | `/api/games/:id`           | Update a game         |
| POST   | `/api/games/:gameId/participants` | Add a participant |
| DELETE | `/api/games/:gameId/participants/:userId` | Remove a participant |
| POST   | `/api/games/:gameId/rounds` | Create the next round |
| POST   | `/api/games/:gameId/score` | Record round scores   |
| GET    | `/api/games/:gameId/score` | Get the scoreboard    |
| GET    | `/api/games/:gameId/score/:userId` | Get a player's score |

```bash

```

### Scoring

Scoring is calculated only by the backend. A winner receives 3 points and each honorable mention receives 1 point; clients submit awards, never point values.

```text
POST /api/games/:gameId/score
GET  /api/games/:gameId/score
GET  /api/games/:gameId/score/:userId
```

The POST body identifies the round, its recorded host, the winning guess, and honorable-mention guesses with display titles:

```json
{
  "round": {
    "id": "<round-uuid>",
    "hostedBy": "<host-user-uuid>",
    "winningGuess": "<guess-uuid>",
    "honorableMentions": [
      {
        "guessId": "<guess-uuid>",
        "title": "Answer was completely on point"
      }
    ]
  }
}
```

Score reads are keyed by user ID. Each player has a running `total` and only rounds where they scored. A round contains its summed `score` and an `entries` array because one player can receive multiple awards in the same round. Reposting a round replaces that round's prior entries atomically, so retries and corrections do not double-score.

### Gameplay mutations

- Creating a game enrolls the authenticated creator and keeps their `activeGames` in sync; admin-only participant add/remove does the same.
- `POST /api/games/:gameId/rounds` assigns the next round number and links the round to the game; the host must be a participant.
- Rounds are finalized through `POST /api/games/:gameId/score`; a finalized round rejects further round updates, guesses, and tier lists with `409 ROUND_FINALIZED`.
- Guess and tier-list submissions upsert: resubmitting replaces that user's previous entry (`201` on create, `200` on replace). One guess per user per round is DB-enforced.
- A tier-list submission from the round host becomes the round's canonical `tierList`; other participants land in `participantTierLists`.

### Remaining UI API gaps

A composite game-state endpoint may be useful if the UI otherwise needs several requests to render one game screen.

## Gameplay authorization

Every `/api/games`, `/api/rounds`, and `/api/tier-lists` handler requires a valid
access-token cookie from Discord login. Missing, invalid, or expired cookies return
`401 UNAUTHORIZED`; authenticated callers without the required role receive
`403 FORBIDDEN` in the shared API error envelope.

- `POST /api/games` accepts `{ name, description, roundCount }`. The session user is
  the admin and sole initial participant. Legacy `createdBy`/`participants` fields
  are ignored; add other users through the admin-only participant endpoint.
- `GET /api/games` filters in the database to games the caller administers or
  participates in. Clients do not need to fetch all games/users to filter access.
- Only `game.createdBy` may edit game settings, manage participants, create rounds,
  or edit round settings (including the assigned host).
- Game, round, tier-list, and score reads require current game membership. An admin
  who is no longer enrolled can still manage the game but cannot read participant
  content. Orphaned rounds/tier lists are not publicly readable.
- Guess and tier-list submission `userId` must match the session user, who must be
  enrolled. Only the recorded round host's submission becomes the canonical list.
- Finalizing awards requires `round.hostedBy` to match both the session user and
  the recorded host. The game admin is not implicitly the round host.

The typed frontend client inherits the reduced create-game body from the shared
schema; submission and scoring callers should continue sending their own user ID.

### Round phases

Round responses expose `phase` and `pendingGuessers`. New rounds start in
`awaiting_host`. The host submits the canonical tier list to open `guessing`,
which snapshots the current non-host players who still owe a guess. Existing
legacy guesses count toward completion. At least one non-host player is required.
The last required guess moves the round to `judging`. Host scoring moves it to
`finalized`, and score corrections retain that phase.

Guesses and replacements are accepted during `guessing` only. Hosts cannot guess.
The canonical host list and round settings lock once guessing opens. Participant
tier lists remain editable during guessing and judging. Phase violations return
409. Round creation requires the previous round to be finalized.

Players added after guessing opens join the guessing roster on the next round.
Removing a pending player removes their obligation and opens judging when all
remaining guesses are in and at least one guess exists. Submission writes and
scoring lock the round row so concurrent actions preserve phase and submission
state. The phase migration backfills existing rounds from their tier lists,
guesses, winners, and current game membership.

### Round deadlines

Set an optional future `endsAt` when creating a round or editing it before the
host submits. A null deadline allows guessing without a time limit. The host's
first submission opens guessing and records the remaining window length.

At the cutoff, rounds with guesses enter `judging`. Late guesses and replacements
receive 409. Empty rounds return to `awaiting_host` with the next different player
in participant order as host. The same round ID and number are retained, previous
tier-list associations are cleared, and their submission events remain in history.
When the replacement host submits, a fresh window of the recorded length starts.
If no other participant exists, the host becomes unassigned so the admin can add
players and assign a host. An expired deadline while still awaiting the original
host must be updated by the admin before that host can submit.

The backend sweeps on startup and every 30 seconds after the previous sweep
completes. Submissions, scoring, and round reads also process expiry, so the
background interval does not allow late guesses. Round locks serialize expiry
with player actions and make repeated sweeps safe across backend instances.
Deadline events use `actor: null` to identify system actions. Scoring preserves
the guessing deadline instead of replacing it with the scoring time.

The migration backfills active rounds' window lengths using the earliest host
submission event, falling back to round creation time for older data. Automatic
next-host selection after a scored round remains follow-up work.

### Guess visibility

`GET /api/rounds/:roundId/guesses` returns `{ ok: true, guesses: [...] }` in
creation order, with IDs breaking timestamp ties. Each guess includes its ID,
round, author, text, and creation/update timestamps. The typed frontend client
exposes `api.getRoundGuesses(roundId)`.

Current game membership is required. Before finalization, players see their own
guesses, and the recorded host sees all guesses during `judging`. After
finalization, all current participants see all guesses. Game administration alone
does not grant access. A player with no visible submission receives an empty list.
The server filters by the authenticated user in the database and processes any
expired deadline under the shared round lock before applying visibility rules.
Responses disable caching. Winner IDs, honorable mentions, and score deltas remain
available through the round and score read endpoints.

## Authentication boundaries

Users are created only after Discord OAuth verifies their identity. `POST /api/users`
is no longer registered. User list/detail reads require a valid access cookie and
remain available to signed-in players for lobby enrollment; they disable caching.
Refresh-token consumption and replacement run in one transaction with a row lock,
so a token can be redeemed once and failed replacement rolls back consumption.
Scoring, including corrections to finalized rounds, requires the recorded host to
remain a game participant. A game-row lock serializes that check with removal.

## PostgreSQL integration tests

Unit tests (`npm test`) need no database. Refresh-token integration tests use the
existing `postgres` client and Drizzle against a real PostgreSQL server, including
two connections competing for the same token and rollback on failed replacement.

From the repository root, run the isolated Docker suite:

```bash
npm run test:integration --workspace @tier-list-league/backend
```

Vitest global setup starts PostgreSQL 17 with Docker Compose on a dynamically
allocated loopback port, waits for readiness, and removes its containers and
volumes after the suite. Tests run locally; no application image build, Discord
credentials, or running application services are required.

Or supply an existing disposable database:

```bash
TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/tier_list_league_test \
  npm run test:integration --workspace @tier-list-league/backend
```

When `TEST_DATABASE_URL` is supplied, global setup uses that database without
starting or stopping Docker. The suite creates a unique schema for each run and
drops that schema afterward. Its database role must be able to create
schemas, tables, and trigger functions. It never uses the application's
`DATABASE_URL` implicitly.
